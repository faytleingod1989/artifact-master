# 圣遗物管理大师问题修复实施文档

## 1. 文档用途

本文档交给后续开发模型或开发人员执行。它来自对当前目录程序的源码、构建结果和运行界面的审查，重点解决“程序能运行，但部分核心结果不可信”的问题。

执行时应先修数据正确性，再修体验问题。不要只改文案、样式或演示数据来绕过验收。

## 2. 当前工程概况

- 前端：React 19 + TypeScript + Vite。
- 桌面端：Electron。
- 本地数据：IndexedDB（`idb-keyval`）和部分 `localStorage`。
- OCR：Tesseract.js，本地单张、批量和实时画面识别。
- 主要源码：`apps/web/src/App.tsx`、`apps/web/src/scoring.ts`、`apps/web/src/realtimeCapture.ts`。
- 当前状态：`npm run build` 和 `npm run lint` 可通过，但项目没有单元测试或端到端测试。

## 3. 修复优先级

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P1 | 评分算法量纲错误、分数过早封顶 | 推荐排序不可信 |
| P1 | 推荐只按部位贪心选择 | 无法满足套装和属性阈值 |
| P1 | OCR 把主词条写进副词条，且遗漏防御词条 | 入库数据错误，进一步污染评分 |

### 3.1 已冻结的实施决定

以下项目按固定方案执行，不再二选一：

- 本期不增加稀有度字段；数据模型只有五星圣遗物时隐藏稀有度筛选。
- 回收站实行自动保留 30 天，过期条目不恢复，不能只改文案。
- JSON 导入采用严格模式。任一核心字段、ID、队列引用或资源记录非法时，整体拒绝导入，原数据保持不变。
- 备份分为 `full` 和 `light`：两者都包含库存、回收站和队列；只有 `full` 包含用户导入的角色头像。
- 圣遗物自定义图标功能移除，原版图标跟随应用发布，不进入用户备份。
- P1、P2 均为本次必须完成项；P3 依赖升级为应完成项。若 P3 受上游依赖阻塞，报告中必须列出漏洞链、影响边界和后续升级条件。

## 4. P1：重做评分计算

### 4.1 问题说明

`apps/web/src/scoring.ts` 的 `numberFromStat` 直接提取面板数字，再乘权重。固定生命值 `4780`、固定攻击力 `311` 和百分比 `46.6%` 被放在同一个量纲内计算。

实际后果：芙宁娜的 +20 生之花仅主词条和等级就会达到 100 分上限，副词条再好或再差都难以区分。元素伤害加成又没有对应 `StatKey`，正确元素杯的主词条得分为 0。

### 4.2 修复要求

1. 把词条解析成结构化数据，不再长期依赖字符串计算：

```ts
type StatValue = {
  key: StatKey
  value: number
  unit: 'flat' | 'percent'
}
```

2. 主词条评分按“是否符合角色、流派和部位需求”计算，不用原始面板数值直接乘权重。
3. 副词条先归一化，再乘角色权重。固定值和百分比必须使用各自的标准区间或等价换算。
4. 增加元素伤害加成、治疗加成等实际会作为主词条出现的类型。
5. 全局 100 分只能在所有维度汇总完成后统一归一化，不能让固定主词条提前封顶。
6. 单件分需要可解释，至少返回：主词条得分、副词条得分、潜力得分、总分、警告和原因。套装得分只出现在组合评分明细中。
7. 规则应带 `ruleVersion`，以后更新角色权重时可以识别旧结果。

最低可执行公式约定如下，后续可以通过版本化规则升级，但不能临时改变：

- 主词条最多 30 分：角色规则中的首选主词条得 30 分，可接受主词条得 15 分，其他得 0 分。
- 词条权重限定在 0～2，且每个角色流派至少有一项大于 0。`maxWeight` 为该流派最大副词条权重。
- 副词条最多 60 分。先用 `rollEquivalent = value / maxRoll[statKey]` 计算等价最高档次数，再计算 `subRaw = Σ(rollEquivalent × weight)`。当前等级理论可见档数为 `availableRolls = min(9, subStats.length + floor(clamp(level, 0, 20) / 4))`，分母为 `availableRolls × maxWeight`，最后 `subScore = min(60, 60 × subRaw / denominator)`。分母为 0 时副词条得 0 分并返回规则错误。
- 项目基线的五星单次最高档表为：暴击率 3.89、暴击伤害 7.77、攻击力% 5.83、生命值% 5.83、防御力% 7.29、元素充能效率 6.48、元素精通 23.31、固定攻击力 19.45、固定生命值 298.75、固定防御力 23.15。该表放入版本化静态数据，不得散落在函数中。
- 胚子潜力最多 10 分。`remainingUpgrades = max(0, 5 - floor(level / 4))`；有效副词条定义为 `weight >= 0.5 × maxWeight`；`potentialScore = 10 × remainingUpgrades / 5 × min(4, effectiveSubStatCount) / 4`。满级时该项自然为 0。
- 套装效果不计入单件分，放到组合推荐阶段计算，避免单件分和组合分重复加成。
- 总分按一位小数四舍五入。缺失或无法解析的词条不计分，并返回警告。

开发评分模块前，先把上述数值表写入版本化配置，并建立至少 10 个黄金样例。黄金样例由公式直接给出各分项期望值，允许误差为 0.1；产品负责人只负责确认角色主词条分类和权重表，不得让实现代码反向生成期望值。

### 4.3 验收用例

- 两件同等级生命花，副词条更适合角色的一件得分必须更高。
- 芙宁娜的生命杯应优先于无效主词条杯；不能因为固定生命数值大而让所有生命花都变成 100 分。
- 火伤角色的火元素伤害杯不能得到 0 主词条分。
- 未强化但有效副词条较多的胚子应能得到“值得强化”，不能只看当前数值。
- 所有角色的五个部位都至少有一组明确的推荐主词条测试。

## 5. P1：重做配装推荐

### 5.1 问题说明

当前 `recommendBuild` 只为每个部位选择单件分数最高的圣遗物，没有处理套装效果、关键属性阈值或多套候选，因此不能称为完整配装推荐。

### 5.2 修复要求

1. 每个部位先取 Top N 候选，建议默认 N=20。
2. 在候选内搜索五件组合，至少考虑：
   - 4 件套和 2+2 套装关系；
   - 角色推荐主词条；
   - 充能、暴击等关键阈值；
   - 同一件圣遗物不能在同一方案中重复；
   - 如果以后支持多角色并行配装，同一件圣遗物不能被多个已锁定方案占用。
3. 最多输出三种方案：综合最佳、输出词条优先、充能或生存优先。库存只有一个或两个可行组合时允许少于三种，但要说明原因。
4. 每种方案显示分数构成、命中的套装效果、未满足的阈值和与当前方案的差异。
5. “最佳”仅表示 Top N 候选集内按当前目标函数得到的最优结果，界面不得暗示全库存穷举最优。库存或规则变化后使缓存失效，缓存键包含库存版本、角色、流派和规则版本。
6. 并列时按满足阈值数量、总分、套装完整度、圣遗物 ID 的固定顺序决胜，保证重复计算结果稳定。

组合评分统一把各分项归一化到 0～100：

- `singleAverage`：五件单件分的平均值。
- `setFit`：命中角色规则中的首选 4 件套为 100；命中可接受 4 件套为 80；命中规则允许的 2+2 为 70；只命中一个首选 2 件套为 35；其余为 0。
- `targetFit`：角色规则把阈值标成 `hard` 或 `soft`。未达到任一 hard 阈值的组合直接淘汰；soft 阈值按 `min(1, actual / target)` 求平均后乘 100。没有 soft 阈值时记为 100。
- 综合最佳：`0.70 × singleAverage + 0.20 × setFit + 0.10 × targetFit`。
- 输出优先：用攻击、暴击、元素伤害和精通等输出词条重算 `outputFit`，结果为 `0.75 × outputFit + 0.15 × setFit + 0.10 × targetFit`。
- 充能或生存优先：用充能、生命和防御等规则目标重算 `utilityFit`，结果为 `0.55 × singleAverage + 0.15 × setFit + 0.30 × utilityFit`。

`outputFit` 和 `utilityFit` 都复用单件评分的归一化公式，只把不属于该分类的词条权重设为 0，再对五件结果求平均。分类后没有任何正权重时，该方案类型不可用，不输出一个人为的 0 分方案。

具体口径：分类单件分不计算胚子潜力，使用 `categoryPieceScore = 100 × (mainScore + subScore) / 90`；其中主词条和副词条都按该分类过滤后的权重重算。`outputFit` 或 `utilityFit` 是五件 `categoryPieceScore` 的平均值。所有阈值的 `actual` 只汇总五件圣遗物提供的属性，不包含角色基础属性、武器、命座、天赋、队伍增益或食物；界面必须写明这一口径。

元素伤害使用独立 `StatKey`，至少区分火、水、冰、雷、风、岩、草和物理伤害，不使用一个无法判断元素的通用键。角色流派规则的最低数据契约为：

```ts
type BuildRule = {
  ruleVersion: string
  preferredMainStats: Partial<Record<Slot, StatKey[]>>
  acceptableMainStats: Partial<Record<Slot, StatKey[]>>
  subStatWeights: Partial<Record<StatKey, number>>
  preferredSets: Array<{ setKeys: ArtifactSetKey[]; pieces: 2 | 4; fit: 100 | 80 | 70 | 35 }>
  thresholds: Array<{ key: StatKey; target: number; kind: 'hard' | 'soft' }>
  outputStats: StatKey[]
  utilityStats: StatKey[]
}
```

每个角色流派配置必须提供首选/可接受主词条、词条权重、套装偏好、hard/soft 阈值和输出/生存词条分类。缺少这些字段的流派不得启用推荐按钮。

### 5.3 验收用例

- 单件分略低但可以组成有效 4 件套时，组合推荐可以优于五件散件。
- 充能低于角色最低阈值的方案不能被标成“综合最佳”而不提示限制。
- 三个目标函数得到不同最优解时分别展示；同一组合同时在多个目标下最优时合并成一张方案，并标注它覆盖的取向，不强行选择次优装备凑数。
- 缺少某个部位时明确显示缺口，不得生成虚假完整方案。

## 6. P1：修复 OCR 结构化入库

### 6.1 问题说明

当前 `saveOcrArtifact` 从 OCR 全文筛选前四个含属性词的行。主词条通常也在这些行中，因此会被再次写入副词条。筛选表达式还遗漏“防御”，导致防御副词条丢失。

`prefillOcrFields` 只取第一条属性相关文本作为主词条。如果 OCR 把“生命值”和“4,780”识别成两行，主词条就不完整。

### 6.2 修复要求

1. 新建独立 OCR 解析模块，不要继续把全部逻辑堆在 `App.tsx`。
2. 解析结果使用结构化草稿：

```ts
type OcrArtifactDraft = {
  name?: string
  setName?: string
  slot?: Slot
  level?: number
  mainStat?: StatValue
  subStats: StatValue[]
  warnings: string[]
}
```

3. 先识别名称、套装、部位、等级和主词条，再从剩余文本中识别副词条。
4. 主词条命中的文本位置必须从副词条候选中排除。
5. 支持生命、攻击、防御、暴击率、暴击伤害、元素充能、元素精通及元素伤害等词条。
6. 合并相邻的属性名和值行，兼容中文冒号、全角加号、空格和常见 OCR 错字。
7. 副词条去重，限制最多四条，并校验数值范围。
8. 不能确定的字段留空并显示警告，禁止猜测后静默入库。
9. 确认表单中必须允许逐项修改四条副词条，而不是让用户编辑整段 OCR 原文来间接修正。

校验分为 error 和 warning：

- error 会阻止保存：名称或主词条缺失；等级不是 0～20 的整数；主词条类型不允许出现在该部位；副词条超过四条、重复、数值小于等于 0；或单条副词条超过 `maxRoll[statKey] × (1 + floor(level / 4))`。
- warning 允许用户确认后保存：套装或部位置信度不足、主词条数值未命中版本化等级表、Tesseract 对相关文字行的置信度低于 70，或存在未能解析的文本行。
- 没有命中合法词条键，或文字行置信度低于 70，均视为“不能确定”。warning 状态下保存前必须勾选“我已逐项核对”。
- 主词条合法类型和各等级数值放入版本化 `game-data` 表。未完成该表时，类型校验仍为 error，精确数值只报 warning，不能伪造精确匹配。

### 6.3 验收用例

- 主词条不会出现在副词条数组中。
- “防御力 +23”和“防御力 +5.8%”都可以正确识别。
- 属性名和值分成两行时可以正确合并。
- 重复 OCR 行只生成一条副词条。
- 超过合法范围的等级和词条值会提示用户确认，不能直接保存。
- 单张、批量和实时 OCR 共用同一个解析与校验模块。

## 7. P1：修复空结果和隐藏选择

### 7.1 问题说明

当前 `visibleArtifacts` 只控制网格内容，`selected` 仍从全部库存中获取。筛选结果为 0 时，界面仍显示“已选中 1/0”，详情、编辑、锁定、强化队列和删除按钮继续作用于不可见条目。

### 7.2 修复要求

- 筛选条件变化后，如果当前选择不在可见结果中：
  - 有可见结果时自动选择第一件；
  - 没有可见结果时把当前选择置空。
- `selected` 为空时显示空详情状态。
- 删除、编辑、锁定、加入队列等按钮必须禁用或隐藏。
- 底部数量应显示“已选中 0 / 0”，不能写死为 1。
- 删除前增加二次确认；已锁定圣遗物的删除按钮直接禁用，必须先执行独立的解锁操作，不允许在删除弹窗内顺便绕过锁定。

### 7.3 验收用例

- 搜索不存在的名称后，没有任何按钮能修改原来选中的圣遗物。
- 清除搜索后恢复正常选择。
- 当前条目被套装或部位筛选隐藏时，选择正确切换到第一件可见条目。
- 删除最后一件可见条目后，详情和选择状态同步更新。

## 8. P2：补齐高级筛选

### 8.1 问题说明

套装和部位筛选有效，但主词条、强化等级和稀有度控件没有状态与过滤逻辑。

### 8.2 修复要求

- 给主词条、最低等级和最高等级建立受控状态。
- 套装、部位、主词条和等级条件在 `visibleArtifacts` 中同时生效。
- 校验等级范围：0 至 20，最低值不能大于最高值。
- “重置”必须恢复所有筛选条件，不只是套装和部位。
- 筛选结果数量实时更新。
- 当前数据模型只有五星圣遗物，因此本期直接隐藏稀有度筛选，不增加虚假的 `rarity` 字段。

### 8.3 验收用例

- 选择“元素伤害加成”后只显示符合的圣遗物。
- 等级 16 至 20 不显示 +0 和 +12 条目。
- 多个条件可以叠加。
- 重置后恢复完整库存。

## 9. P2：升级 JSON 导入导出

### 9.1 问题说明

当前备份包含 `artifacts`、`trash` 和 `assets`，没有强化队列。导入新仓库后，旧 `queueIds` 仍保留，若新旧数据出现相同 ID，会把旧队列错误绑定到新条目。

### 9.2 修复要求

1. 定义版本化备份格式，建议升级为 version 2：

```ts
type BackupBaseV2 = {
  schemaVersion: 2
  exportedAt: string
  artifacts: Artifact[]
  trash: TrashedArtifact[]
  queueIds: number[]
  characterProfiles: CharacterProfile[]
}

type LibraryBackupV2 =
  | (BackupBaseV2 & { mode: 'light'; characterAssets: [] })
  | (BackupBaseV2 & { mode: 'full'; characterAssets: CharacterAssetBackup[] })
```

2. 导出当前所有结构化用户数据，强化队列和角色档案不能遗漏。角色头像是否包含由 `mode` 决定。
3. 导入前完整解析和校验，不要在校验完成前修改任何 React 状态或本地存储。
4. 校验 `trash`、`queueIds`、资源格式、唯一 ID 和数组长度。任一核心校验失败时整体拒绝导入，不做自动修复。
5. 导入失败时保持旧仓库原样，不能出现部分替换。
6. 导入成功时用备份队列替换旧队列；旧版备份没有队列时使用空队列，并提示用户。
7. 增加从 version 1 到 version 2 的迁移函数。
8. 增加 `setName -> setKey` 别名表和本地数据库 `schemaVersion`。本地启动迁移采用“先快照、后暂存、校验通过再提交”的流程；未知套装保留原记录但移入隔离区，不进入活动库存。外部 version 1 JSON 出现未知套装时整体拒绝导入，只生成不落库的迁移报告。
9. 迁移必须幂等。同一份旧数据重复运行迁移，结果不能重复增加或改变 ID。
10. 原版圣遗物图标不进入备份；`characterAssets` 只允许角色头像，记录角色键、MIME、字节数和 SHA-256。
11. 导入 `light` 备份时保留角色档案，但清空其中的自定义头像引用并回退到内置 Q 版头像，同时在导入报告中列出。导入 `full` 时头像记录必须全部通过校验，否则整体拒绝。
12. 严格边界固定为：`artifacts` 最多 5000 条、`trash` 最多 5000 条、`queueIds` 最多 5 条、`characterProfiles` 最多 100 条、`characterAssets` 最多 100 条；名称、套装、主词条和每条副词条字符串最多 100 个 Unicode 字符。
13. `light` 文件最大 12 MB；`full` 文件最大 40 MB，其中全部角色头像解码后总量最大 32 MB。头像只接受 PNG、JPEG、WebP，单张最大 3 MB、宽高各不超过 4096 像素，并且必须能真实解码。MIME、文件签名和实际解码格式必须一致。

### 9.3 验收用例

- 导出后清空本地数据再导入，库存、尚未过期的回收站条目、队列和角色档案全部恢复；`full` 还应恢复角色头像，`light` 清空自定义头像引用并恢复内置 Q 版头像。
- 导入损坏 JSON 后本地数据没有任何变化。
- 重复 ID、非法部位、非法等级和不存在的队列 ID 会导致整体导入被拒绝。
- 旧版备份可以迁移，但不会继承导入前的旧队列。
- 用固定时钟测试回收站边界：导入时已过期的条目不恢复，并出现在导入报告中。

## 10. P2：实现回收站 30 天策略

### 10.1 问题说明

删除时虽然写入 `deletedAt`，但 `Artifact` 类型不包含该字段，代码通过类型断言绕过检查；加载数据时也没有清理超过 30 天的条目。

### 10.2 修复要求

- 新建明确类型：

```ts
type TrashedArtifact = Artifact & {
  deletedAt: number
}
```

- 程序启动、打开回收站和导入备份时都执行过期清理。
- 过期规则使用删除时间加 30×24 小时，写成可单元测试的纯函数。
- 回收站显示剩余天数或到期日期。
- 永久清空继续要求二次确认。
- 边界固定为 `now >= deletedAt + 30天` 时过期。未来时间、非数字时间或明显异常时间视为损坏数据，严格导入时拒绝，本地启动迁移时进入隔离报告。

## 11. P2：调整本地图片存储

### 11.1 问题说明

用户图片以 Data URL 写入 `localStorage`。单张允许 3 MB，多张图片容易超过浏览器配额；写入失败时缺少清晰错误和事务回滚。本节只处理用户导入的角色头像，圣遗物自定义覆盖按原版图标文档移除。

### 11.2 修复要求

- 图片 Blob 存入 IndexedDB，不再把大图放入 `localStorage`。
- 元数据与图片内容分开存储。
- 导入前检查图片格式、真实解码结果、尺寸和体积。
- 捕获配额错误，向用户说明原因；失败时不更新界面状态。
- 启动时把现有角色头像 Data URL 迁移到 IndexedDB：先写入并校验 Blob，再切换引用，最后删除旧键。失败时继续读取旧值并允许重试。
- 旧的 `artifact:<id>` 覆盖只进入迁移报告，不再用于渲染；确认新版原版图正常后再清理。
- 设置页提供“清理旧圣遗物自定义图”按钮，展示待清理数量和预计释放空间，并要求二次确认。用户未点击前旧数据保留但不参与渲染；不以弹窗或自动定时任务代替该按钮。
- 垃圾回收只处理角色头像 Blob，并根据当前角色头像引用执行；回收站中的圣遗物不再依赖自定义图。
- `full` 备份包含角色头像并显示预计大小，`light` 备份不包含角色头像。两种模式的恢复保证必须在导出界面写清楚。

## 结论与范围

有值得优先优化的地方。首先是备份恢复的数据校验和保存失败后的处理，其次是启动入口、强化队列的操作闭环，最后是大库存下的响应速度。不建议先换框架、重写架构或调整评分权重。

本轮由 gpt-6-astra 负责拆分、指挥与复核，两位 gpt-6.1-sol 分别检查前端/录入/性能，以及持久化/恢复/Electron 边界；主代理独立核对启动交付、资源隔离与回归基线。检查以代码、局部内存复现及现有测试为依据。

本轮没有修改产品源码、评分规则、用户配置或实际用户数据库，没有查询真实 UID，没有重新打包或发布。仅新增本报告。以下优先级是建议修复顺序，不代表已修复。

## 优先处理的六项

### 1. P1：JSON 导入校验比持久读取宽，异常备份能让程序失去可用性

位置：`apps/web/src/App.tsx:47`、`:202`；`apps/web/src/storage/libraryRepository.ts:8`、`:14`；`apps/web/src/scoring.ts:34`、`:58`。

触发条件：用户导入被修改、损坏或非严格匹配的数据。例如一条记录的副词条为 `subs: [null]`，或本地编号为 `id: 42.5`。无需真实 UID 或外部网络。

证据：Sol 提取实际导入谓词与实际评分模块做纯内存复现。两种记录均通过 App 的 JSON 校验；`subs: [null]` 进入推荐计算后抛出 `Cannot read properties of null (reading 'replaceAll')`。小数 ID 能通过导入，但会被仓库重新加载时的 `Number.isSafeInteger` 校验拒绝。主代理独立复核了这条数据路径。

用户影响：非法副词条会造成渲染异常；若小数 ID 已保存，下次打开会进入仓库读取失败状态。不是“普通备份必然损坏”，而是导入入口不能可靠阻止坏数据污染本地状态。

建议：导入和持久读取共用结构校验；在替换状态前检查副词条元素、安全整数 ID、跨仓库/回收站 ID 唯一性。先完成全量校验，再执行保存和界面切换。保留旧格式兼容，不借修复强行改写旧词条或重算评分。

验收：非法输入不改变原库存；错误定位到具体记录；合法旧备份、空库、回收站备份继续恢复；退出再打开仍正常。

### 2. P1：推荐启动入口打开的是公开构建，不是个人原图版

位置：`启动圣遗物管理大师.vbs:7`、`:11`；`本地版使用说明.md:5`。

触发条件：按根目录说明双击启动器。

证据：启动器只遍历 `apps/web/release` 的子目录，选择遇到的第一个 EXE，完全不检查 `release-local`。本轮目录检查确认目前匹配的是 `release/win-unpacked` 中的公开构建；不是凭日期推测“必然旧版”。说明文件写出的 `release/圣遗物管理大师-win32-x64/圣遗物管理大师.exe` 目录目前不存在。

用户影响：用户以为打开了含个人原图的版本，实际进入公开构建；这会被误认为原图丢失或更新没有生效。说明还保留旧实时流程、旧截图入口和单件图标上传操作，没有准确介绍 UID 展柜导入及自动辅助默认关闭。

建议：启动器使用明确的交付目标，个人入口优先指向已核实的 `release-local/ArtifactMaster-0.1.0-avatars-20261001-local.exe`；缺少目标时明确提示，不扫描任意 EXE 兜底。同时更新使用说明，保留公开/个人构建隔离规则。

验收：根入口打开个人版；个人包缺失不误开公开版；说明中每个按钮名、路径和默认行为与当前程序一致。此项不要求删除旧包。

### 3. P2：保存失败后提示“重试”，但没有直接重试当前修改的入口

位置：`apps/web/src/App.tsx:110`、`:116`、`:247`。

触发条件：锁定、移入回收站、调整队列或 JSON 恢复引起自动保存，而本次 IndexedDB 写入失败。

证据：失败回调清空保存签名并设置错误，但 effect 依赖仍只有库存、队列、读取完成状态与回收站。仅设置错误不会重新保存。重试按钮只在 `!storageReady` 时出现，而保存失败仍保持 `storageReady=true`。Sol 对实际 effect 的内存故障注入结果为 `writes=1`、`ready=true`、重试按钮条件为 `false`。

用户影响：界面已有修改，却没有落盘；即使临时故障恢复，用户也不能直接重试。再次修改其他数据可能带动重存，但关闭程序会丢失尚未保存的修改。统一录入确认页已有失败重试，本项针对普通自动保存，不混为一谈。

建议：提供“重试保存当前修改”，明确区分待保存、已保存、保存失败；重试使用当前内存快照，不重新读取旧库存覆盖用户未落盘的内容。成功后清除旧错误提示。

验收：注入一次写入失败后，不增加额外业务修改即可重试成功；重开能看到原修改；失败状态仍能导出当前数据备份。

### 4. P2：JSON 恢复后遗留旧队列 ID，可能指向另一件藏品

位置：`apps/web/src/App.tsx:121`、`:185`、`:211`。

触发条件：当前队列已有条目，随后用另一份 JSON 替换仓库；新备份包含相同 ID 但不同内容的记录。

证据：导出的 JSON 含库存、回收站和头像，不含 `queueIds`；导入替换库存和回收站，却没有恢复或清理旧队列。实际导入函数的内存复现中，旧队列 `[42]` 在恢复后仍为 `[42]`，解析到的是备份中的另一件、且已满级的藏品。

用户影响：队列显示与用户原先选择不一致；换设备时队列也无法从备份还原。即使正常备份的数据结构合法，也能触发此问题。

建议：先确定备份承诺。若备份整个仓库状态，增加版本兼容的队列字段，并验证引用；旧备份没有队列时采取明确的清理策略，不能默默继承另一库存的队列。是否自动剔除满级记录属于规则选择，应单独确认。

验收：同 ID 不同内容、无 ID 交集、旧版不含队列及含队列新备份均有明确结果；恢复后队列不能错误绑定。

### 5. P2：强化队列可放五件，但只显示三件且没有移除入口

位置：`apps/web/src/App.tsx:127`、`:132`、`:254`、`:256`、`:263`。

触发条件：将四至五件未满级藏品加入队列，或队列满后继续加入。

证据：加入逻辑截断为五件，界面却用 `queuedArtifacts.slice(0, 3)`；“管理”和“查看强化建议”都只是滚动到现有队列区域。检查完整状态变更路径，没有单独退出队列的操作。满五件后新 ID 被截断，无说明。

用户影响：数量显示可达 5/5，但第四、第五件不可见；用户不能正常整理队列，也不知道新加入为何无效。把藏品移入回收站会顺带移除队列，但不能作为队列管理方式。

建议：展示全部五件，提供单项移除/清空队列，满额时给出反馈。若暂不做完整管理界面，至少修正显示数量和按钮含义。

验收：五件均可见、可逐项移除，不改变库存本体；第六件加入有明确提示；重复加入不新增重复项。

### 6. P2：大库存下排序与导入去重有可量化的主线程计算成本

位置：`apps/web/src/warehouse/warehouseModel.ts:8`、`:14`、`:22`；`apps/web/src/imports/ImportReview.tsx:10`、`:24`；`apps/web/src/artifacts/artifactDraft.ts:69`。

触发条件：库存接近 JSON 入口允许的 5000 件，按双暴排序，或同时核对 20 件录入草稿。

证据：Sol 在 Windows、Node v24.14.0 下，以 Vite `ssrLoadModule` 加载现有源码，使用内存合成记录测量；没有读取实际用户库。5000 件三轮双暴排序为 412.745 / 341.199 / 368.285 ms；对 20 件草稿逐件扫描 5000 件库存去重为 910.334 / 886.465 / 984.045 ms，1000 件五轮约 165～194 ms。排序比较器反复解析同一副词条；确认组件在每次编辑后的渲染中对每个草稿重新扫描库存，转换还会为比较生成无用 UUID。`UidShowcaseImport.tsx:26` 的每秒计时更新在确认阶段仍运行，也会重复触发这部分工作。

这些是本机纯函数样本，不含 React 渲染、DOM 或 OCR，不是生产 P95，也不能据此断言所有用户启动卡顿。它说明在允许的数据规模内，单次计算已值得优化。

建议：一次生成每条藏品的排序指标；按库存变化建立指纹到 ID 的索引，编辑某条草稿时仅重算该条；确认阶段暂停无用的计时刷新。先保持排序、去重和评分结果完全相同，再视真实浏览器测量决定是否需要列表虚拟化或按需加载。

验收：固定 1000/5000 件样本比较优化前后耗时，记录环境和多次结果；输出顺序、重复 ID 列表、未知词条处理不变；另外测真实浏览器输入与滚动。

- 桌面外链：`electron/main.cjs:29` 将新窗口 URL 交给 `shell.openExternal`，没有协议允许列表。当前检查未找到不可信动态链接或 HTML 注入的可达路径，属于纵深防御建议，不宣称已存在可利用的远程代码执行。
- 推荐能力：`scoring.ts:60` 起是逐部位独立取最高分，不是完整套装/循环/伤害优化器；仓库已显示“规则初评候选（不代表最优配装）”。本轮没有改变角色权重，不用UI中的“综合评分最高”推导实战最优。
- 导航可再精简：“查看方案”“查看全部”等按钮目前主要滚回已有区域。应让按钮直接带用户到已有候选视图，或使用更准确的文案，不需要为此新增复杂页面。

- P3，内部 API 防御：`capture/captureController.ts:52` 在 `await stop()` 后才获取启动代际。实源内存并发调用两次 `start()` 后再 `dispose()`，创建两组流/worker，但停止与释放计数均为 `[0,1]`，第一组引用被覆盖。普通 UI 有 busy 禁用保护，本轮未证明正常点击可触发，不能称真实游戏采集故障。后续可在等待前取得唯一代际或同步排他，并释放过期初始化结果。

## 建议实施顺序

第一阶段处理坏备份校验、保存失败重试、队列恢复规则，同时纠正启动入口与说明。对这些具体问题补故障注入测试，不改数据语义和评分。

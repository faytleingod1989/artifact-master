# 借鉴 yas 的采集与 OCR 优化设计

日期：2026-10-19。状态：待用户审阅；仅设计与计划，尚未实施。

## 1. 目标和范围

让现有 Windows 本地圣遗物管理程序录入更快、更省操作，同时保留真实图片、严格校验和用户确认。优先解决已有 F8 录入的耗时和识别问题，再增加独立的当前页批量扫描模式；不重写仓库、角色配装、评分和潜力算法。

本轮提出分期方案，不把计划中的能力写成已完成。P0/P1 为首期交付，P2 为第二期，需要先完成自动鼠标操作的设计审阅；P3 自动翻页仅为后续候选，不随本轮默认实施。

## 3. 方案选择

1. **推荐：保留 Electron 管理界面，优化现有本地 OCR，增加可插拔专用识别路径。** 先完成自动字段切分和现有模型的行识别，再引入通过授权、字表、准确率和耗时门槛的轻量模型。只改变采集／识别层。
2. **备选：使用独立 yas 扫描并导入结果。** 接入面小，但扫描体验和错误恢复分离；不是用户当前偏好的实时录入方式，不作为主方案，也不新增 GOOD 导入为强制步骤。
3. **不采用：将整个程序改写成 Rust。** 改动范围远超当前瓶颈，无法由此保证识别更准或更快。

默认依次完成 P0 → P1；P2 依赖首期接口稳定并获得实施确认。授权无法澄清时，首期仍可交付独立实现的字段切分与 PP-OCRv5 行识别，不无限等待上游模型。

## 4. 必须保留的行为

- 仅收入五星；截图／手动／UID 导入、角色档案、评分和潜力功能不退化。
- 保留 F8 截图排队、捕获音和识别成功音，游戏前台不抢焦点。
- 同一图片的重试不能重新采集当前画面；不同任务不能串图或被迟到回调复活。
- 保留每批最多 20 个未入库任务、单张编码源图 16 MiB、源图合计 128 MiB 的限制。
- 属性数值不猜测、不自动四舍五入；6.5% 合法，6.59% 不能静默改成 6.5%；名称规范化与数字处理分开。
- 三条有效副词条和待激活第四条是正常情况；待激活属性不计入当前已生效评分。
- 两件属性完全相同的真实圣遗物必须可以分别保留；只能提示疑似重复，不能按属性集合自动删重。
- 高置信且完整的结果自动填好待确认摘要；低置信项保留原图并允许重识别，不强制用户从头填写全部字段。确认前不入库。
- 全部 OCR 离线，不上传图片、不运行时下载模型、不自动提权、不静默切换捕获来源。
- 不读取游戏内存、不注入、不绕过保护机制；不能据此承诺游戏规则或反作弊层面的绝对安全。
- 不存在 Git 仓库：不初始化、不执行 Git 提交，只记录修改清单、测试证据与发布清单。

## 5. P0：准确的桌面基准和诊断

现有 `scripts/benchmark-artifact-ocr.mjs` 默认在普通 Chromium 中创建 OCR 会话，没有注入桌面桥，因此不能将其结果直接当作桌面原生 PP-OCRv5 基准。保留该测试，但新增真实原生工作进程入口，经过 `nativeOcrService`、解析器和严格校验后再计数。

分别记录冷启动、取帧、定位、编码／传输、文本检测、文字识别、解析、排队及总耗时；不把排队耗时混入模型推理。每组记录机器、模型哈希、样本哈希、分辨率、路径和回退次数。

使用现有原始截图及历史问题样本。至少覆盖五部位、+0/+17/+20、三／四条副属性、待激活行、6.5%、浅色背包卡片和蓝色装备详情。原始图片、界面回放图、裁剪／缩放衍生图分别标记；衍生图不冒充独立真实样本。数据仅私有保存。

验收使用两个指标：整件所有必需字段完全正确率，以及错误结果被标记“可确认”的数量。后者在固定负例集必须为 0；主动拒识单独计数，不能靠全部拒识提高准确率。

## 6. P1：首期识别与取帧优化

### 6.1 自动字段定位和快速识别

标准布局先自动判定“背包浅色卡片／角色蓝色详情”，再产生原图坐标中的字段框。复用现有 `artifactOcrImage.ts`、`cardDetailOcr.ts` 和文字行分析，不复制第二套互相矛盾的规则。定位不确定时走现有通用检测路径，不要求用户框选。

OCR 工作进程新增行识别路径：接收一张详情图及有界字段框，解码一次，按字段裁剪识别；不要为每一行独立往返 Electron IPC。先使用现有 PP-OCRv5 识别器跳过检测器，随后再接入已通过门槛的专用小模型。模型和推理会话只初始化一次。

上游 SVTR 贪心输出没有现成可直接套用的本项目置信度，必须对字段级可信度做样本校准，不能复用 PP-OCR 的 0.75 阈值冒充等价。只对可靠字段采用快路径；字表不足、布局不符、数字歧义或低置信时，对同一张图片进行一次通用识别复核。仍不可靠则失败，禁止无限串行重试。

同一字段不同路径数值冲突时必须报告冲突，不通过挑选合法数值“修好”图片。新旧路径共用待激活解析、合法数值校验和遮挡判断。

### 6.2 精简取帧与传输

先测量现有 `desktopCapturer.getSources()` 每次枚举／高分辨率缩略图的成本，来源枚举只用于选择，避免把枚举当连续截图接口。

为已选择的窗口建立持久帧会话，帧必须来自所选来源。沿用现有可用路径作为可见回退，禁止改拍整个屏幕来掩盖窗口错误。窗口来源无法建立帧会话时，保留原快照路径并报告实际性能。

源图和定位结果绑定来源、帧尺寸和布局版本；尺寸、DPI、窗口位置／布局变化后重新定位。只有每帧轻量验证通过才复用字段区域。先保证不串帧，再减少 PNG／base64 重复转换；不同时重写截图、OCR、IPC 的全部协议。用户成功捕获提示只能在真实帧冻结、预算核验完成后播放。

### 6.3 首期验收门槛

- 历史核心回归图：必需字段及待激活状态全部正确；负例误接受 0。
- 真实样本至少 10 张、覆盖五部位，整件完全正确率不低于原生基线；发布目标为至少 95%。样本不足 30 张时必须报告实际 n/N，不宣称泛化准确率。
- 固定离线样本同机预热一次后测 5 轮，中位数与 P95 分开报告；端到端耗时目标较基线降低至少 30%，这是目标而非当前已达成事实。回退样本不得隐藏在统计之外。
- 实时取帧成功时间单独统计，不能用“后台排队不阻塞”替代提速证据；20 张真实固定帧压力测试不丢、不串、不超资源预算。
- 新路径不满足正确率门槛时不设为默认；性能目标未达成时如实登记阻塞阶段并保留旧路径，不发布为“提速已完成”。

## 7. P2：当前页自动扫描

用户体验：选择原神窗口 → 打开背包、保持页面静止 → 启动当前页扫描 → 切回游戏 → 逐格选中并截图排队 → 本页结束提示 → 用户手动翻页并明确继续。首版不自动滚动。

这是新增鼠标控制能力，必须是用户主动开启的独立模式，默认关闭，仅限已确认的游戏窗口，不支持以整个屏幕作为自动点击目标。原神前台运行测试只能在用户同意并在场的情况下进行。

主进程／原生控制器拥有目标窗口身份和点击坐标；renderer 只能提出开始、暂停、继续、停止，不开放任意坐标点击的通用 IPC。每次输入前复核窗口句柄、进程身份、前台状态及客户区尺寸。失焦、窗口变化、分辨率变化、未知布局立即暂停，绝不激活／追着其他窗口点击。

状态为 idle → armed → scanning → paused／page-complete／stopped；OCR 队列仍由原控制器持有。首次点击前必须等目标窗口成为前台，不主动抢焦点。支持界面停止与鼠标右键紧急停止，停止检测独立于耗时 OCR；不允许停止后继续发送后续点击。F8 不暗改为其他功能，扫描期间暂停其手动截图入口并明确提示，暂停／结束自动扫描后恢复原注册。

不采用单点颜色或属性文字相等作为唯一的切换依据：结合选中格位置和详情局部稳定变化；同属性的相邻两件也应分别处理。超时不采上一件冒充下一件，应暂停并显示未完成位置。

每格记录行列、状态、对应 jobId。队列容量不足时先暂停，不点击下一格；用户核对或丢弃释放容量后，只在页面签名仍匹配时继续。已截图任务仍处理；不自动确认入库来腾位置。页面签名采用列表图标／格位结构而非动态角色背景，同属性实体不能仅靠字段哈希视为同一件。无法确定是否原页时要求重新开始该页并提示可能重复。

锁定状态、装备角色仅作为可选识别字段：无法确认则显示未知，不能默认当作未锁定或未装备，不阻塞核心属性入待确认。首版只读这些状态，不改变游戏中的锁定／装备。

第二期验收：模拟窗口证明只点击预期格位且能中断；受控真实游戏中复核至少一整页的顺序、实际数量、异常暂停、容量暂停续扫和同属性两件保留。模拟或离线回放通过不等于真实窗口已验收。

## 8. P3：后续候选，不纳入本轮默认交付

自动滚动翻页、滚动后行对齐、跨页重复／漏扫检测。只有 P2 稳定后再单独设计和确认，不能顺手增加。角色建议、属性权重、GOOD 导入、整程序 Rust 改写、自动强化／自动锁定均不属于此次优化。

## 9. 发布与回退

首期与第二期分别出可验收版本，不等自动翻页完成才交付。新旧识别路径可通过配置回退，原有库存格式不迁移，功能开关不能修改库存。

打包校验必须同时覆盖引擎类型、模型与字表哈希、许可文件和离线资源；不能只改前端引擎显示名称。使用真实打包程序做离线冒烟测试，确认无外网请求、队列与双音正常。

交付一份报告：样本准确率、误接受／拒识数、耗时分位数、回退比例、内存峰值、测试命令、新程序路径与 SHA256。旧 EXE 仅在新包验证完成、旧进程退出且目标路径确认后按用户既有意愿回收；不动用户数据、截图、依赖运行时或正在使用的程序。

# 圣遗物管理大师：仓库与录入改版设计

日期：2026-10-01。状态：用户已确认设计；待按实施计划开发。本文描述拟实现内容，不代表功能已经完成。

## 1. 已确认目标与边界

个人本地 Windows 使用，只收入五星圣遗物。仓库采用用户已确认的第 2、3 版融合布局：顶部导航、左侧筛选、中间仓库、右侧详情/对比、底部多选操作。原有本地数据和 JSON 备份继续可用，不为改版清空仓库。

录入方式以最新用户决定为准：

- 主入口：实时采集、便捷手动录入。
- 新增：UID 公开角色展柜导入。
- 保留次级入口：单张/批量截图识别。
- 不新增 GOOD 导入；JSON 备份恢复不属于 GOOD。

UID 查询是用户明确新增的可选联网功能，修订此前“不读取 UID”的限制，但不授权读取游戏内存、客户端文件、账号凭据、Cookie、Token 或网络封包。仓库、手动录入和实时采集不依赖 UID 服务；本地 OCR 的资源须随包提供才能验收离线可用。

## 2. 视觉目标与仓库交互

已确认的融合概念图：`C:/Users/Administrator/.codex/generated_images/019fec2f-3572-7992-9235-fb4d948c41aa/exec-19d2d435-100e-4b36-b2ee-165b203e6607.png`。实施时复制到项目设计资料目录留存。它是布局与视觉参考；图中文字、示例数量和游戏数据不能当作数据真值。

保留深蓝、米白、少量暗金；高亮有效词条使用青色。常用文字不小于 14px。主工具栏为“实时采集”“手动录入”“UID 展柜导入”，截图放在“更多录入”内，备份操作放入仓库菜单。

### 2.1 两种表示，同一份仓库

- 图标视图：原图、套装/部位、等级、主词条、四个副词条、锁定和勾选状态。
- 列表视图：小图、套装/部位、等级、主词条、四个副词条、双暴、锁定；数值对齐，可按等级、双暴和充能副词条排序。
- “图标视图 / 列表视图”使用有文字标签的切换按钮。
- 切换只影响表示方式，保留搜索、筛选、排序、选中详情和多选集合；在本机记住视图偏好。
- 筛选至少覆盖套装、部位、主词条、等级范围、锁定；不再出现无效的四星筛选或没有绑定行为的筛选控件。
- 不匹配筛选的项目不显示为当前详情；结果为空时显示明确空状态，不引用不存在的选中项。

“全部库存 / 按角色查看”沿用现有角色规则作为辅助查看方式，明确标为规则初评。不要把当前逐部位最高分算法包装成精确伤害优化；全面重做配装算法另行规划。

### 2.2 详情与比较

右侧可切换详情和两件对比，关闭对比返回详情。不同部位仍可浏览，但不作为直接替换比较；跨部位选择时说明原因。对比显示主、副词条及差值，不直接宣称哪件必然更好，不自动修改游戏装备。

双暴仅计算副词条：`2 × 暴击率 + 暴击伤害`，不计入主词条。百分比差值以“百分点”表达。+20 显示“已满级”，不再提示继续强化。未核实的套装效果不显示伪造说明；删除所有套装共用“攻击力提高18%”的硬编码文案。

### 2.3 原版图标不变形

所有界面共用 `ArtifactGlyph` 和“套装 + 部位”映射。图片等比缩放、居中、完整显示；使用 `object-fit: contain`，禁止拉伸、非等比变换、裁切主体、改变原色和以其他套装图冒充。

容器可以是正方形，图片自身比例不能被容器改变；列表图标不得被弹性布局压扁。长羽毛、花、冠、沙、杯分别检查，小图、大图和不同窗口宽度均须通过。

本地自用构建须能加载已收集的私有原版素材，不能再因生产模式排除素材而全部变成占位图。区分本地私有构建与公开构建，公开构建继续遵守原有素材隔离检查，不把本地素材随意提交或用于公开发布。未知套装显示明确缺图/数据待补状态。

## 3. 统一录入草稿与确认流程

三种主录入方式和次级截图入口都进入同一套结构化草稿、校验和入库流程：

`采集/手填/查询 → 草稿 → 校验 → 疑似重复预览 → 用户确认 → 本地入库`

草稿至少包含套装键、部位、五星、等级、主词条类型与数值、副词条列表、来源类型；UID 草稿可附角色 ID 和查询时间。使用独立稳定本地 ID，不只依赖同一毫秒的时间戳，避免批量入库冲突。

保留现有记录格式的迁移兼容及 JSON 导出。新录入数值使用统一结构解析后转换到当前存储格式；不能在仓库、OCR 和 UID 里各自维护不同词条解析规则。

校验包括：等级为 0～20 整数、该部位主词条合法、至多四条副词条且类型不重复、副词条类型不能与主词条相同、数值有限且在五星合法范围。与等级成长表不符时明确提示，不能自动修成猜测值。解析失败的必填项禁止保存。

套装和部位能确定时优先使用核实过的单件名称；没有核实的单件名称则显示“套装·部位”，不编造名称。旧数据不因改版被静默更名或删除，修正应有迁移记录。

相同套装、部位、等级、主副词条可标为疑似重复，但不能证明是同一件游戏物品。重复项默认不勾选，提供“跳过 / 作为另一件新增 / 明确选择更新已有记录”；不覆盖整库、不自动合并、取消不写入。主界面显示入库和跳过数量。

## 4. 实时采集

用户选择可见游戏窗口，明确启动后采集。默认以 F8 主动采集为主，自动检测作为可关闭的辅助选项，避免无意捕获重复画面。程序不模拟游戏鼠标键盘、不自动翻背包。

识别使用原画面的详情区域，避免先把完整画面缩到 1280 再裁切而丢失文字清晰度。选中圣遗物图标不作为权威图源；入库后的图标仍由套装/部位映射决定。支持采集区域校准和可见预览，无法定位时提示调整窗口/区域或手动录入，不猜字段。

状态明确区分未启动、采集中、识别中、待确认、失败、停止。F8 快捷键冲突时给出提示；识别未完成时的再次按键串行处理，不能并发写入。停止、取消、窗口关闭时释放流、快捷键和临时图片。

待确认批次保留现有最多20件限制；达到上限提示先确认或清理。确认页左侧原图区域、右侧结构化词条；低置信度及规则异常单独标出，OCR 原文折叠为诊断信息。校对期间不删除必要预览；条目保存、丢弃或批次取消后及时释放图片，不作为默认永久数据保存。

## 5. 便捷手动录入

套装可搜索，部位决定主词条选项；选择主词条后数值从等级成长表建议填入，允许修正并校验。花固定生命值主词条，羽固定攻击力主词条；其他部位只给合法选项。

四行副词条均为“类型下拉 + 数值输入”，百分号单位由类型决定，不要求用户输入完整句子。已选类型从其他行排除，零级三副词条合法；四行无需全部填写。

支持键盘 Tab 顺序、“保存”“保存并继续”、复制当前件为新草稿。连续录入可保留套装/部位偏好，但必须清空上一件数值和唯一 ID，避免误重复。名称不是必填自由输入；优先按已核实目录生成。

## 6. UID 展柜导入

### 6.1 用户流程与隐私

输入 UID → 明确点击“查询公开展柜” → 展示角色和五星装备 → 勾选确认 → 合并到本地仓库。

查询按钮旁明确说明：将 UID 发给第三方 Enka.Network，只获取公开角色展柜，不是官方服务或整个背包。不开机自动查、不在输入时查询、不要求账号登录/密码/Cookie/Token、不枚举 UID、不上传本地仓库。

默认只在本次操作的内存里保留 UID 和查询响应；“记住 UID”由用户主动勾选，仅本地保存，默认关闭。角色 ID、装备来源类型和查询时间可以本地保存；个人简介、签名、成就等与录入无关的数据不持久化，也不写日志。导入后离线仍能查看和管理装备。

### 6.2 接入与解析

桌面版通过专用 Electron IPC 调用固定 HTTPS Enka UID 接口，主进程负责请求；保留 contextIsolation、sandbox 和禁用 nodeIntegration。校验 IPC 来源和 UID，仅允许固定主机/路径，不提供任意 URL 代理，不跟随跳转到其他主机。

设置产品专用 User-Agent；请求超时15秒，单次响应限制5MB，同 UID 请求进行中不得重复。按响应 `ttl` 做内存缓存与刷新倒计时，429尊重 Retry-After/退避，不自动反复重试。浏览器版只显示桌面版能力提示，不用不可信公共代理规避跨域。

只解析 `avatarInfoList[*].equipList` 中 `flat.itemType === ITEM_RELIQUARY` 且 `flat.rankLevel === 5` 的装备；武器和低星装备跳过，显示跳过数量。用版本化本地中文字典解析套装/单件名 hash 和角色 ID；未知项目单独列出并阻止该项入库，不让一件未知装备阻断其他有效项目。

部位按 API 枚举映射：BRACER=花、NECKLACE=羽、SHOES=沙、RING=杯、DRESS=冠。接口 `reliquary.level` 范围1～21，显示/保存为接口值减1。词条使用 `flat.reliquaryMainstat`、`flat.reliquarySubstats` 的明确类型和 `propValue`，不要对百分比再盲目乘100。

接口未提供的游戏锁定状态不能推断为“已锁定”；本工具本地锁定由用户自行设置。只根据明确字段建立角色来源关联，不依靠头像名称猜测。

### 6.3 失败与缓存反馈

离线、UID格式错误、角色不存在、展柜关闭/为空、服务维护、429、超时、异常响应分别给出可理解提示。全部失败路径保持现有仓库不变。缓存数据注明查询时间和刷新等待，不能宣称游戏内换装立即实时同步。

技术依据（2026-10-01核查）：

- [Enka接口与访问规则](https://github.com/EnkaNetwork/API-docs/blob/master/api.md)：固定UID端点、User-Agent、限流、ttl、错误码与空展柜。
- [原神装备字段定义](https://github.com/EnkaNetwork/API-docs/blob/master/docs/gi/api.md)：角色展柜、装备类型、等级、部位和词条。

## 7. 实施模块与范围控制

沿用 React/Vite/Electron/IndexedDB，不换框架。仅把本次涉及的职责从过大的 `App.tsx` 拆开：

- 仓库组件：筛选、图标/列表、选中状态、详情/比较；视图偏好独立于装备记录。
- 统一词条与草稿模块：格式化、校验、双暴、重复检查、存储兼容。
- 手动录入与统一确认组件：不让来源分别绕过校验。
- 实时采集：采集会话、区域预览和串行任务。
- Enka适配器：固定目标请求、数据转换、错误、缓存；与页面和本地仓库解耦。

本次不增加完整伤害模拟、自动游戏操作、GOOD、云同步、微信登录或移动端独立工程。不把草案角色规则升级为未经验证的权威推荐；已有功能不能因为重构被悄悄移除。

## 8. 验收标准与顺序

1. 仓库及图标：两种视图真实切换、状态保留、多选对比有效；1440×920及最小980×680无主要操作遮挡；本地Windows包原图正确加载且五部位不变形。
2. 手动录入：五部位、三/四副词条、非法组合、连续保存、复制草稿、刷新后保存结果可用；现有备份迁移不丢数据。
3. UID导入：固定脱敏响应样本覆盖五部位、等级换算、百分比、未知数据、低星过滤、重复确认、空展柜、ttl与限流；桌面实测查询成功。需要实际查询时只使用用户主动提供的UID，不从历史截图提取来测试。
4. 实时采集：用真实中文详情截图先建立标注样本，再测实际OCR，不能仅用模拟文本代替识别验收。至少10张、覆盖五部位，包含用户此前问题图对应字段；所有必填字段完全正确条目达到9/10，错误条目必须被拦到待核对。用户原始问题图当前路径不存在，需要实施验收时重新提供，不影响先做其他工作。
5. 发布：类型检查、单元/组件测试、静态检查、构建和Windows运行均通过；本地私有/公开构建素材检查各自符合边界。记录真实测试结果及剩余限制，不以构建通过代替OCR准确性或联网能力成功。

建议按“仓库与手动录入 → UID导入 → 实时采集质量 → Windows验收”推进；各块单独验收。具体文件任务与执行方法在本文审阅通过后形成实施计划。
